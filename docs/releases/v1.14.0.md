## Relio v1.14.0 — 메일 알림, 로그인 계정 노출 차단, 조회 오류 안전장치

열려 있던 자동 개선 PR 네 건을 현재 코드(v1.13.0)에 맞춰 통합하고, 통합하면서 드러난 문제를 함께 고쳤습니다. MCP OAuth를 다룬 PR #25는 v1.12.0에 같은 기능이 반영되어 닫았습니다. 같은 Keycloak 26.4 환경에서 이 PR은 표준 클라이언트의 로그인이 `invalid_scope`로 거부되었습니다.

## 1. 사내 SMTP 릴레이로 메일 알림 (#23)

**기본값은 꺼짐**입니다. **기본 설정 → 메일 알림**에서 릴레이 주소와 보낼 이벤트를 켭니다.

| 이벤트 | 받는 사람 |
|---|---|
| 승인 요청 | 승인자 |
| 승인 결과 | 요청자 |
| 고객 요청 배정 | 다른 사람이 배정한 새 담당자 |
| 계약 갱신 임박(미착수) | 계약 담당자, 계약당 한 번, 담당자별로 묶어서 |

동작 방식:

- 발송은 요청과 분리된 백그라운드에서 이뤄져 화면을 기다리게 하지 않습니다.
- 시도마다 성공·실패만 기록하고 본문은 저장하지 않습니다.
- 비밀번호는 암호화 설정으로 저장되며 응답·감사 로그에 드러나지 않습니다.
- 자기가 한 행동은 자기에게 알리지 않습니다.
- **시험 발송**과 **발송 기록**을 관리자 화면에서 확인합니다.

통합하며 반영한 점:

- **마이그레이션 번호를 `017`로 조정**했습니다. `015`와 `016`은 이미 v1.12.0·v1.13.0이 쓰고 있습니다. 같은 번호여도 적용은 되지만, 표시되는 스키마 버전이 가장 높은 파일명 기준이라 016에 머물렀을 것입니다.
- v1.13.0 **부서 업무 영역의 SLA 미적용 유형**은 배정 메일에 응답 기한 줄을 넣지 않습니다. 일반 요청 메일에는 그대로 들어갑니다(실측 확인).

## 2. 로그인 응답으로 비상 관리자 계정명이 드러나던 문제 (#24)

일반 로컬 로그인을 꺼 두면, 로그인 API가 비밀번호를 확인하기 전에 응답을 갈랐습니다. 없는 아이디와 일반 사용자에게는 `403 local_login_disabled`를, 비상 관리자 아이디에는 비밀번호 검사 결과를 돌려줬습니다. 그래서 비밀번호를 몰라도 **어느 아이디가 비상 관리자인지** 알 수 있었습니다.

이제 비밀번호를 먼저 확인합니다. 비밀번호를 증명하지 못한 시도는 모두 같은 `401 invalid_credentials`이고, 정책에 따른 `403`은 올바른 비밀번호를 댄 일반 사용자에게만 나갑니다. 실측 결과는 다음과 같습니다.

- 없는 아이디, 틀린 비밀번호, 비상 관리자의 틀린 비밀번호 → 모두 401
- 일반 사용자의 올바른 비밀번호 → 403
- 비상 관리자의 올바른 비밀번호 → 로그인

CI에 `gofmt` 위반 시 빌드를 실패시키는 검사도 추가했습니다.

## 3. 조회 중 끊긴 결과가 정상 목록처럼 보이던 문제 (#29)

DB 결과를 읽다 연결이 끊기면, 일부만 읽은 목록이 성공 응답으로 나갈 수 있었습니다. 다음 조회 경로에서 끊김을 오류로 돌려줍니다.

- 고객 360, Forecast
- 사용자·Role·조직·감사 로그·사용자 정의 항목 목록
- 세션·내 활동, 키 일괄 폐기

같은 규칙을 코드 전체에 강제하는 정적 검사도 추가했습니다. v1.13.0의 VOC 업무 영역 코드도 이 검사를 통과했습니다.

## 4. 저장소 접근이 막힌 브라우저에서 로그인·로그아웃이 깨지던 문제 (#28 + 보완)

사생활 보호 모드처럼 브라우저 저장소가 막히면 로그인 화면 렌더링이 실패했습니다(#28).

통합하면서 같은 원인의 나머지 세 곳도 고쳤습니다.

- 로그인 전 원래 경로를 기억하는 곳
- 로그인 후 그 경로로 돌아가는 곳
- **로그아웃이 중간에 멈춰** 로그인 상태가 풀리지 않던 곳(저장소 삭제가 `finally` 안에서 실패)

이제 저장소가 막혀도 기억한 경로만 잃고, 로그인과 로그아웃은 정상 동작합니다.

JSON 본문이 한도를 넘으면 두 번째 해석 단계에서도 `413 request_too_large`로 답합니다(#28).
