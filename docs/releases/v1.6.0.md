## Relio v1.6.0 — Portable Encryption Key, SSO 정상화, 관리자 전체 CRUD

Relio v1.6.0은 세 가지 운영 결함을 해결합니다. 재기동·Volume 재생성 때마다 API Key를 다시 발급해야 했던 문제, 일반 사용자가 SSO로 로그인하면 403이 발생했던 문제, 그리고 관리자 화면의 여러 리소스가 조회·생성만 가능했던 문제입니다.

> 이 Release는 v1.5.0 다음 버전입니다. Tag 없이 작업만 완료되어 있던 v1.5.1의 Master Key 무결성 검증과 Secret 저장 안전성 개선도 모두 포함하므로, v1.5.0에서 바로 업그레이드하면 됩니다.

## 1. ENCRYPTION_KEY — 자격증명 영속성

### Envelope 구조 도입

암호화와 HMAC에 실제로 쓰이는 **Instance Data Key**를 Wrapping Key와 분리했습니다. Data Key는 설치 시 한 번 생성된 후 변하지 않고, 봉인된 형태로 `instance_data_key`에 저장됩니다.

| 구성 | 재기동 | 이미지 교체 | `relio-data` Volume 재생성 |
| --- | --- | --- | --- |
| `ENCRYPTION_KEY` 설정 | 유지 | 유지 | **유지** |
| 미설정 (`master.key` 파일만) | 유지 | 유지 | 복구 필요 |

- 네 번째 환경변수 `ENCRYPTION_KEY`를 추가했습니다. 필수 3개는 그대로이며 이 값은 선택입니다.
- 64자리 16진수, Base64로 인코딩한 32바이트를 그대로 사용하고, 그 밖의 값은 32자 이상일 때만 HKDF-SHA256으로 도출합니다.
- Key 값은 로그, Support Bundle, Configuration Bundle, Admin API 어디에도 나타나지 않고 단방향 지문만 PostgreSQL에 남습니다.
- Wrapping Key를 바꿔도 Data Key는 그대로이므로 **이미 발급한 Personal Key와 저장된 SSO Client Secret은 재발급 없이 계속 유효합니다.**

### 무중단 이관과 Fail-Closed

- 기존 Volume이 연결된 상태에서 `ENCRYPTION_KEY`를 처음 설정하면 첫 기동에서 자동으로 이관(Adopt)됩니다. 별도 마이그레이션 명령이 없습니다.
- 이관·회전 이력은 `instance_data_key_events`에 Key 값 없이 기록됩니다.
- 잘못된 `ENCRYPTION_KEY`, 값 누락, 다른 Volume, 손상된 암호문은 모두 새 Key를 만들지 않고 기동을 중단합니다.
- 오류 메시지가 무엇을 복구해야 하는지 지목합니다. Data Key가 `ENCRYPTION_KEY`로 봉인되어 있으면 Volume 복구 대신 그 값을 다시 주입하라고 안내합니다.
- `/admin/operations`에 Data Key ID, 봉인 방식, Wrapping Key ID를 표시하고, 아직 Volume에 종속된 배포에는 `ENCRYPTION_KEY` 설정을 권고합니다.

## 2. SSO 일반 사용자 403 오류 수정

### 원인

Keycloak SSO로 자동 생성된 사용자에게 Role이 하나도 부여되지 않았습니다. 인증은 성공하지만 Permission이 비어 있어 Dashboard(`opportunity:read`)를 포함한 모든 API가 403을 반환했습니다. Claim Mapping과 OIDC Default Role을 모두 비워 둔 기본 설정에서 항상 재현됩니다.

### 수정

- 기본 Role `SALES_USER`(영업 담당자, USER Scope)와 `SALES_MANAGER`(영업 팀장, TEAM Scope)를 기본 제공합니다.
- `roles.is_default`로 **신규 Sign-in 기본 Role**을 지정합니다. Claim 매핑이 하나도 맞지 않으면 이 Role을 부여합니다.
- 부여 순서를 Claim 매핑 → OIDC Default Role → 기본 Sign-in Role로 정리했습니다. 이전에는 Default Role과 매핑 Role이 항상 함께 부여됐습니다.
- Role이 하나도 없으면 자동 생성을 진행하지 않고 명확한 오류를 반환합니다.
- 이미 Role 없이 만들어진 기존 SSO 계정은 마이그레이션에서 기본 Role을 부여하고, 재로그인 시에도 자체 복구합니다.
- OIDC 설정 화면의 `Default Role ID` 자유 입력을 Role 선택 목록으로 교체하고, 자동 생성이 켜져 있는데 기본 Role이 없으면 경고를 표시합니다.
- SSO Callback 실패를 `not_provisioned`, `no_default_role`, `discovery_failed`, `token_exchange_failed`, `token_invalid`, `claim_missing`, `state_expired`로 구분해 로그인 화면에 원인별 안내를 표시합니다. 이전에는 모든 실패가 같은 문구였습니다.
- 권한이 전혀 없는 계정은 깨진 화면 대신 요청 방법을 안내하는 전용 화면을 표시합니다.

## 3. 관리자 화면 전체 CRUD

조회·생성만 가능했던 리소스에 수정과 삭제를 추가했습니다. 파괴적 작업은 참조 무결성을 깨지 않으며, 무엇이 연결되어 있는지 건수와 함께 알려줍니다.

| 리소스 | 추가된 기능 |
| --- | --- |
| 사용자 | 정보 수정, 비활성화(Session·Personal Key 즉시 폐기), Role 부여 화면, 임시 비밀번호 재설정 |
| 조직 | 생성 화면, 수정, 삭제, 순환 참조 차단 |
| Role | 생성, 권한·Data Scope 편집, 삭제, 기본 Sign-in Role 지정 |
| Pipeline | 생성, 수정, 삭제, 기본 Pipeline 승격 |
| Pipeline Stage | 편집, 순서 재배치, 삭제, Won/Lost 단일성 보장 |
| Custom Field | 수정, 삭제, Select 항목 편집 |
| 승인 정책 | 수정, 삭제(이력이 있으면 비활성화) |
| 시스템 설정 | 삭제로 기본값 복원 |
| 상품 | 신규 관리 화면 + 등록·수정·삭제(사용 중이면 판매중지) |

### 안전장치

- Bootstrap Break Glass 계정은 비활성화·삭제·Role 전체 제거가 모두 차단됩니다. 관리자 본인 계정도 비활성화할 수 없습니다.
- 삭제는 이름·Code 입력 확인을 요구합니다.
- Role 권한을 바꾸면 해당 사용자의 Session을 종료해 이전 권한이 만료까지 남지 않게 합니다.
- 비활성화한 사용자의 Session과 활성 Personal Key를 함께 폐기합니다.
- 비밀번호 재설정 시 모든 Session을 종료하고 다음 로그인에서 변경을 강제합니다.
- 시스템 Role은 `admin:*` 유지를 강제하고 삭제를 차단합니다. 기본 Sign-in Role, 기본 Pipeline, 최상위 RELIO 조직도 삭제할 수 없습니다.
- Stage 삭제·비활성화는 진행 중 Opportunity와 Forecast Snapshot 참조를 확인합니다. Pipeline은 마지막 Stage를 남깁니다.
- 열거하지 못한 참조는 PostgreSQL Foreign Key 위반을 관리자 문장으로 번역해 안내합니다.
- 새 `/api/v1/admin/permissions`로 부여 가능한 권한 카탈로그를 제공하고, 잘못된 권한 문자열 저장을 차단합니다. 오타로 아무 권한도 없는 Role이 만들어지는 상황을 막습니다.

## 4. 미구현 기능 완성 및 개선

- Customer 360과 고객 목록의 **편집** 버튼이 동작합니다. 이전에는 Handler가 없는 장식 버튼이었습니다.
- Opportunity Drawer의 **편집** 버튼과 전용 수정 화면을 추가했습니다.
- 고객 목록의 고객유형·등급 Filter가 실제로 동작합니다. 서버에 `customerType`, `grade` 조건을 추가했습니다.
- 영업활동 화면의 활동 유형 Filter가 동작합니다. 서버에 `type` 조건을 추가했습니다.
- 상단 알림 Bell이 실제 알림 목록을 열고 읽음 처리와 대상 이동을 수행합니다.
- 관리자 Pipeline 화면이 비활성 Pipeline도 표시해 다시 활성화할 수 있습니다. 이전에는 비활성화하면 화면에서 사라져 편집이 불가능했습니다.
- Role 카드에 사용자 수를 표시합니다.
- v1.2에서 대체된 `CustomerDetail`, `OpportunityDrawer` Dead Code를 제거했습니다.
- OpenAPI 문서에 새 관리자 CRUD 및 상품 Endpoint를 반영했습니다.

## 5. v1.5.0에서 함께 반영되는 변경 (구 v1.5.1)

### Master Key와 PostgreSQL 결합 검증

- Data Key의 Domain-separated SHA-256 지문을 `instance_key_registry`에 등록하고 시작 시 상수 시간으로 비교합니다.
- 활성 Personal Key, OIDC Client Secret 또는 암호화 System Setting이 있는데 열 수 있는 Key가 없으면 새 Key를 생성하지 않습니다.
- Master Key 파일이 32바이트 일반 파일인지 확인하고 Symlink를 거부합니다.
- 지문 등록 이전 버전에서 올라오는 환경은 기존 암호문을 실제로 복호화해 Key를 식별한 뒤 등록합니다.

### SSO와 Secret 저장 안전성

- OIDC 설정 화면에서 Client Secret을 비워 저장하면 기존 암호문을 보존합니다.
- 기존 Secret 보존을 위한 DB 조회 오류를 더 이상 무시하지 않습니다.
- OIDC 설정과 System Setting에 Version 기반 Optimistic Lock을 적용해 여러 관리자 화면의 동시 저장이 최신 설정이나 Secret을 덮어쓰지 않게 했습니다.
- Secret Setting은 빈 Mask 입력 시 기존 값을 유지하고, Secret 속성을 평문으로 바꾸는 요청을 차단하며, 변경 전 Audit 값도 `***`로 기록합니다.
- OIDC 자동 프로비저닝이 Group/Role Mapping 조회·할당 오류를 무시해 권한 없는 사용자를 남길 수 있던 문제를 수정했습니다.

### 운영 진단

- Persistent Storage 진단이 Directory 존재 여부뿐 아니라 PostgreSQL 보안 ID와의 일치까지 확인합니다.
- 시작 로그는 Key 원문 없이 Key ID, 보호 자격증명 수, 신규 생성·이관 여부를 구조화해 기록합니다.

## 발견 및 수정한 오류

- `ENCRYPTION_KEY`가 없어 `relio-data`를 잃으면 모든 Personal Key와 SSO Client Secret을 재발급해야 했던 문제
- SSO 자동 생성 사용자가 Role 없이 만들어져 로그인 후 모든 화면이 403이던 문제
- OIDC Default Role과 Claim 매핑 Role이 중복 부여되던 문제
- 관리자 Pipeline 화면이 `p.active=true`만 조회해 비활성 Pipeline을 편집할 수 없던 문제
- 사용자를 비활성화해도 기존 Session과 Personal Key가 계속 동작하던 문제
- Role 권한을 축소해도 기존 Session에서 이전 권한이 유지되던 문제
- 모든 SSO 실패가 동일한 문구로 표시되어 계정 미등록과 Keycloak 장애를 구분할 수 없던 문제
- 편집·필터 버튼이 Handler 없이 배치되어 눌러도 반응하지 않던 문제

## 업그레이드 절차

1. PostgreSQL과 `relio-data` Volume을 백업합니다.
2. `openssl rand -hex 32`로 `ENCRYPTION_KEY`를 한 번 생성해 비밀번호 관리 도구에 보관합니다.
3. 기존 `relio-data`를 그대로 연결한 상태로 `ENCRYPTION_KEY`를 추가해 Container를 교체합니다.
4. 로그에서 `instance data key re-wrapped with the new wrapping key`를 확인합니다.
5. `/admin/operations`에서 `보호 방식 = ENCRYPTION_KEY (Volume 독립)`과 Schema `007_default_signin_role.sql`을 확인합니다.
6. `/admin/roles`에서 기본 Sign-in Role이 조직 정책에 맞는지 확인하고, 필요하면 Role의 권한과 Data Scope를 조정합니다.

`ENCRYPTION_KEY`를 설정하지 않아도 기존과 동일하게 동작합니다. 이 경우 `relio-data` Volume을 계속 PostgreSQL과 같은 시점으로 백업해야 합니다.
