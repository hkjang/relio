## Relio v1.15.3 — MCP 민원 커스텀 필드 스키마 수정

REST에서는 커스텀 필드를 포함해 접수할 수 있지만 MCP 게이트웨이가 `fields.<키>: Expected never`로 거부하던 문제를 수정했습니다. UI나 업무 설정값을 변경하지 않는 민원 도구 스키마 중심의 수정입니다.

## 원인과 변경

- 기본 민원(업무 영역 없음)의 활성 커스텀 필드를 MCP 스키마 생성에서 누락했습니다. 부서 업무 영역이 없으면 `fields`가 `properties: {}`, `additionalProperties: false`로 공개되어 모든 키를 차단했습니다.
- `file_customer_voice`는 기본 민원과 접근 가능한 업무 영역의 접수 항목을, `resolve_customer_voice`는 해결 항목을 공개합니다. `search_voice_knowledge`의 스키마와 서버 검색 조건에도 기본 민원 필드를 연결했습니다.
- `get_voice_categories`에 기본 민원 정의를 담은 `fields`를 추가했습니다. 기존 `categories`, `workspaces`, `causeEvidence` 응답은 유지합니다. `key`·필수 여부·허용값·기본값을 확인하고 정의된 키 그대로 전달할 수 있습니다.
- 같은 키가 여러 영역에 있을 때 기존 `anyOf` 표현을 유지합니다. 실제 접수·해결은 선택한 유형의 필수값과 허용값을 검사하며, 다른 부서의 필드 정의·데이터는 공개하지 않습니다.
- 필드 조회 오류를 성공한 빈 스키마로 바꾸지 않습니다. 도구 목록 조회에 오류와 재시도 안내를 반환하고 개인 연동 키 화면도 불완전한 목록을 표시하지 않습니다.
- 접수·해결·검색 스키마가 한 번 조회한 정의를 공유하고 MCP 응답에 `Cache-Control: no-store`를 적용합니다. 승인 안내와 쓰기 도구 표시, 지식 검토 권한·상태 전이·접근 범위 검증은 유지합니다.

## 검증

- 기본 필드만 존재하는 환경의 스키마, 접수·해결 단계 분리, 기본/부서 간 동일 키의 허용값 병합, 조회 실패 시 오류 반환을 Go 테스트로 검증
- 공개 v1.15.2 이미지에서 REST 성공/MCP 스키마 거부를 재현하고, 동일 DB·키로 수정 이미지에 교체 후 `jsonschema 4.26.0`의 `Draft202012Validator`로 전체 도구 스키마와 실제 접수 인자 검증·저장·재조회 성공 확인
- 격리 환경에서 `PHONE`, `POPUP_MOD`, `R3001` 테스트 정의로 스키마 사전 검사 → MCP 접수 → REST 재조회 및 저장값 일치 확인
- 필수값 누락·미등록 키·잘못된 허용값·camelCase 별칭·UUID 키 거부, 해결 필드 저장, 오류코드 기반 지식 검색 확인
- 필드 허용값 변경·비활성화 후 서버 재기동 없이 `tools/list` 갱신, 타 부서 인증에서 비공개 필드·허용값 제외 및 직접 ID 접수 거부 확인
- Go 전체 Test·Vet, 프런트엔드 Typecheck·66개 테스트·Production Build, npm audit, 환경변수·외부 정적 자산 계약 검사
- 오프라인 신규 설치·CRM/MCP 회귀·키 지속성, 이전 공개 릴리스 v1.15.2 → v1.15.3 업그레이드 검사

## 업그레이드 및 게이트웨이 갱신

추가 DB 마이그레이션이나 필드 재생성, 키 재발급은 필요하지 않습니다. 기존 릴리스와 동일한 단일 오프라인 Docker 이미지 압축 파일을 제공합니다. 운영 환경의 실제 이미지 교체는 릴리스 발행과 별도입니다.

**서버 교체 후 게이트웨이/챗봇의 Relio 도구 목록도 다시 불러와야 합니다.** 기존 연결이 오래된 스키마를 캐시할 수 있습니다. 재탐색하거나 연결을 끊고 다시 연결한 다음, 실제 접수 인증의 `tools/list`에서 `file_customer_voice.inputSchema.properties.fields.properties`에 필요한 키가 있는지 확인하세요. 서버는 목록 변경 알림을 제공하지 않으므로 캐시가 자동 갱신된다고 가정하면 안 됩니다.

`get_voice_categories`가 반환한 `key`를 그대로 사용합니다. 정의된 키가 `service_type`, `dev_method`, `error_code`라면 이 키를 사용하며 camelCase나 필드 ID로 바꾸지 않습니다. 운영의 허용값·필수 여부·업무 영역 설정은 임의 변경하지 않습니다.
