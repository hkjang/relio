## Relio v1.11.4 — Qwen·OpenCode가 실제로 도구를 읽도록

v1.11.3에서 MCP 프로토콜 버전 협상을 고쳤지만 OpenCode는 여전히 인증 직후 `Failed to get tools`로 연결이 끝났습니다. 이번 릴리스는 설치된 Qwen Code와 OpenCode를 서버에 직접 연결해 원인을 분리했고, 도구 스키마와 클라이언트별 설정을 함께 바로잡았습니다. 발급한 키의 권한 변경, 영업기회 분석 화면의 읽기 흐름, 멈춰 있던 자동 인텔리전스 분석도 함께 개선했습니다.

## 1. OpenCode `failed to parse json` / `Failed to get tools`

### 실제 클라이언트 재현

동일한 v1.11.3 서버와 동일한 Personal Key에 두 클라이언트를 연결했습니다.

| 클라이언트 | 초기화 | `tools/list` | 결과 |
| --- | --- | --- | --- |
| Qwen Code 0.20.1 | 성공 | 성공 | Connected |
| OpenCode 1.17.13 | 성공 | 서버는 200으로 응답 | `Failed to get tools` |

서버의 MCP 요청 로그에는 OpenCode의 `initialize`, `notifications/initialized`, `tools/list`가 모두 성공으로 남았습니다. 전송이나 인증 문제가 아니라, 클라이언트가 받은 도구 정의를 검증하는 단계의 문제였습니다.

### 원인

선택 입력만 있는 도구의 JSON Schema가 다음과 같이 직렬화되었습니다.

```json
{
  "type": "object",
  "properties": { "query": { "type": "string" } },
  "required": null,
  "additionalProperties": false
}
```

JSON Schema의 `required`는 존재한다면 문자열 배열이어야 합니다. Qwen은 이를 허용했지만 OpenCode는 도구 목록 전체를 거부했습니다.

### 수정

- 필수 입력이 없는 도구는 `required` 필드를 완전히 생략합니다.
- 필수 입력이 있는 도구만 `required: ["..."]` 배열을 반환합니다.
- 두 경우를 단위 테스트로 고정하고 오프라인 통합 테스트에서 모든 도구의 `required`가 `null`이 아님을 검사합니다.

수정 이미지에서 같은 OpenCode 명령을 다시 실행해 `connected`를 확인했습니다.

## 2. Qwen과 OpenCode 설정을 따로 제공

기존 안내는 모든 클라이언트에 `mcp-remote` Bridge 설정 하나만 보여주었습니다. 네이티브 원격 HTTP를 지원하는 두 클라이언트에는 오히려 설정 실수를 만들 수 있었습니다.

개인 연동 키의 **MCP 사용 안내 → 클라이언트 설정**에 다음을 각각 제공합니다.

- **Qwen Code**: CLI 명령과 `mcpServers.relio.httpUrl`, `headers.Authorization`
- **OpenCode**: CLI 명령과 `mcp.relio.type: remote`, `url`, `oauth: false`, `headers`
- **stdio 전용 클라이언트**: 필요할 때만 사용하는 `mcp-remote` Bridge

특히 Qwen의 `url`은 구형 SSE 전송이며 Streamable HTTP에는 `httpUrl`을 써야 한다는 점, OpenCode CLI Header는 `KEY=VALUE` 형식이라는 점을 화면과 사용자 안내서에 명시했습니다.

## 3. 발급 후 키 권한 변경

키는 한 번 발급하면 회전하거나 폐기하는 것만 가능했습니다. 에이전트 역할이 바뀔 때 Secret까지 다시 배포해야 했고, 과도한 권한을 발견해도 즉시 줄일 수 없었습니다.

### 현재

- 개인 연동 키 목록에 **권한** 작업 추가
- 기존 Secret을 유지한 채 REST/MCP 채널과 Scope 변경
- 변경 내용은 다음 API·MCP 요청부터 즉시 적용
- 사용자 본인이 가진 권한만 선택지에 표시
- MCP 채널과 `mcp:use`가 어긋난 요청은 서버에서도 거부
- Scope와 Channel 중복·대소문자를 서버에서 정규화
- 변경 전후 Scope·Channel을 `personal_key_history`와 Audit Log에 기록

`PUT /api/v1/me/keys/{id}`는 `version`을 받아 낙관적 잠금을 적용합니다. 두 브라우저 탭에서 같은 키를 편집해 이전 상태로 권한을 되돌리는 보안상 위험을 막습니다.

## 4. 영업기회 분석 읽기 흐름

`팀장 검토 대기`, `영업 코칭` 제목과 설명이 같은 덩어리처럼 보이고 Table Panel 테두리에도 가까웠습니다.

- 분석 Table Header에 상하·좌우 여백을 별도로 부여
- 제목과 설명 사이를 9px로 고정하고 설명의 행간을 확대
- `팀장 검토 대기 3건`, `영업 코칭 5명`처럼 검토 규모를 제목 옆에 표시
- 설명을 `위험 점수 순 · 권장 행동 우선`, `담당자별 실행 공백 · 1:1 코칭 기준`으로 바꿔 팀장이 다음 행동을 바로 이해하도록 개선

1440px 실제 브라우저에서 두 영역 모두 제목과 설명 간격 9px, Panel Header 20/22px Padding을 확인했습니다.

## 5. 자동 CRM 인텔리전스 분석 복구

검증 서버 로그에서 매분 다음 오류가 발생하는 것을 추가로 발견했습니다.

```text
failed to encode args[0]: unable to encode 15 into text format for text
```

자동 분석 주기의 숫자 파라미터를 문자열 연결로 PostgreSQL Interval에 전달해 타입 추론이 실패했습니다. `make_interval(mins => $1::int)`로 바꿔 자동 분석이 정상 완료되도록 했습니다. 실제 PostgreSQL에서 기존 실행 이력을 비운 뒤 재기동해 `SCHEDULE` 분석이 오류 없이 완료되는 것까지 확인했습니다.

- Personal Key 정규화·Bootstrap Scope 단위 테스트
- 실제 Qwen Code 0.20.1: 네이티브 Streamable HTTP `Connected`
- 실제 OpenCode 1.17.13: 수정 전 `Failed to get tools`, 수정 후 `connected`

- 실제 브라우저: 권한 편집 모달과 영업기회 분석 제목·설명 간격 확인
- 완전 격리 Network 신규 설치 Smoke Test와 v1.11.3 업그레이드 Test

## 업그레이드

`012_personal_key_access_version.sql`이 기존 `personal_keys`에 `version = 1`을 추가합니다. 기존 Personal Key의 Secret, Scope, Channel, 만료일은 그대로 유지되며 재발급할 필요가 없습니다.

Qwen은 제품 안내의 `httpUrl` 설정을, OpenCode는 `type: remote` 설정을 사용하십시오. v1.11.3 설정에서 `mcp-remote`가 정상 동작 중이라면 반드시 바꿀 필요는 없지만 네이티브 설정을 권장합니다.
