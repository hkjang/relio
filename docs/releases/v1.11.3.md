## Relio v1.11.3 — 인증은 되는데 도구 목록이 안 되던 이유

MCP 클라이언트가 붙기는 하는데 도구 목록에서 실패하던 문제를 고쳤습니다. 원인은 프로토콜 버전 협상이었고, 같은 계열의 결함 두 개가 더 있었습니다. 키 발급 화면과 MCP 사용 안내도 함께 정리했습니다.

## 1. 프로토콜 버전 협상 — 보고된 증상의 원인

### 재현

클라이언트가 `2024-11-05`로 초기화를 요청하는 상황을 그대로 재현했습니다.

```
initialize (protocolVersion: 2024-11-05)          → 200  ✅ 인증 성공
  서버 응답: protocolVersion "2025-11-25"          ← 요청을 무시하고 자기 최신 버전을 응답
tools/list (MCP-Protocol-Version: 2024-11-05)     → 400  ❌ "지원하지 않는 MCP 프로토콜 버전입니다"
```

### 무엇이 잘못이었나

두 가지가 겹쳤습니다.

1. **협상하지 않았습니다.** 클라이언트가 무엇을 요청하든 서버는 자기 최신 버전을 응답했습니다. 명세는 서버가 지원하는 버전이면 **클라이언트가 요청한 버전으로 응답**하도록 합니다.
2. **`2024-11-05`를 지원 목록에서 빠뜨렸습니다.** 여전히 여러 클라이언트가 이 버전으로 협상합니다.

그 결과 클라이언트는 자기가 아는 버전을 헤더에 담아 보내고, 서버는 그 버전을 거부했습니다. 인증은 성공하고 이후 모든 호출이 실패하는 정확한 형태가 됩니다.

### 수정

- 지원 버전: `2025-11-25`, `2025-06-18`, `2025-03-26`, **`2024-11-05`**
- 클라이언트가 요청한 버전을 그대로 응답하고, 모르는 버전이면 자기 최신을 응답합니다
- 버전 거부는 HTTP 오류가 아니라 **JSON-RPC 오류**로 반환합니다. 클라이언트는 JSON-RPC를 읽지 HTTP 본문을 읽지 않습니다

## 2. 같은 계열의 결함 둘

### Accept 헤더가 지나치게 엄격했습니다

`application/json`과 `text/event-stream`을 **둘 다** 요구했습니다. 명세가 클라이언트에게 요구하는 내용이지만, 이 서버는 모든 응답을 JSON으로만 보내고 스트림을 열지 않습니다. `application/json`만 보내는 클라이언트를 406으로 막을 이유가 없었습니다.

이제 JSON을 받을 수 없다고 명시한 클라이언트만 거부합니다.

### JSON-RPC 배치를 처리하지 못했습니다

`2025-06-18` 이전 리비전은 배열 형태의 배치 요청을 허용하고, 클라이언트는 여전히 보냅니다. 서버는 이를 **잘못된 JSON으로 취급**해 400을 반환했습니다.

```
[{"jsonrpc":"2.0","id":1,"method":"tools/list"}]  → 400 invalid_json
```

단건과 배치를 모두 처리하고, 배치에는 배열로 응답합니다. 알림(id 없는 메시지)은 응답에서 제외됩니다.

## 3. 도구 실패와 전송 오류를 구분

도구가 실행되어 실패한 경우까지 JSON-RPC 오류(`-32000`)로 반환하고 있었습니다. 명세는 이것을 **`isError: true`를 담은 정상 결과**로 돌려주도록 합니다. 권한 거부나 검증 실패는 모델이 읽고 대처할 수 있는 정보인데, 전송 오류로 만들면 대화가 그냥 끊깁니다.

| 상황 | 이전 | 현재 |
| --- | --- | --- |
| 없는 도구 이름 | `-32000` | `-32602` (프로토콜 오류) |
| 도구 실행 실패 | `-32000` | `isError: true` 결과 |
| 잘못된 파라미터 | `-32000` | `-32602` |

MCP 요청 로그는 `isError` 결과도 실패로 집계합니다. 그렇지 않으면 모든 실패가 성공으로 기록됩니다.

## 4. 전수 검증에서 잡은 것

키 하나에 23개 Scope를 부여하고 **읽기 도구 33개를 실제로 호출**했습니다. 그 과정에서 드라이버 오류 문자열이 그대로 노출되는 것을 발견했습니다.

```
no rows in result set
```

에이전트는 이것으로 "레코드가 없음"과 "서버 고장"을 구분할 수 없습니다. REST와 MCP 양쪽에서 `요청한 데이터를 찾을 수 없거나 접근 권한이 없습니다.`로 바꿨습니다.

도구 42개의 스키마도 함께 검사했습니다 — 이름·설명·`inputSchema` 누락 0건, `readOnlyHint` 누락 0건, `required`에만 있고 `properties`에 없는 필드 0건.

## 5. 키 발급 화면

### 이전

Scope 30개가 원시 문자열로 나열된 평면 체크박스 격자였습니다. 아무도 코드 서른 개를 읽지 않습니다. 전부 켜거나, 너무 적게 켜고 며칠 뒤에 에이전트가 동작하지 않는 이유를 찾게 됩니다.

### 현재

- **도메인별 그룹**과 그룹 단위 전체 선택 (부분 선택은 중간 상태로 표시)
- **전체 선택 / 전체 해제**
- **조회 전체 선택 / 해제**, **입력 전체 선택 / 해제**
- 프리셋: `조회 전용 에이전트`, `영업 자동화`, `고객 요청 처리`, `최소 권한`
- 각 항목에 `조회` · `등록·수정` · `삭제` 같은 한국어 동작명을 붙이고, 데이터를 바꿀 수 있는 항목은 색으로 구분
- 하단 요약: `14개 선택됨 · 조회 전용입니다` 또는 `이 중 6개는 데이터를 변경할 수 있습니다`
- MCP 채널을 켜면 `mcp:use`가 자동 포함됩니다. 이것이 빠진 키는 인증에 성공한 뒤 모든 호출이 거부되는데, 원인을 찾기 어려운 종류의 실수입니다

## 6. MCP 사용 안내 모달

개인 연동 키 화면과 키 발급 창에서 열 수 있습니다.

| 탭 | 내용 |
| --- | --- |
| 연결 | 엔드포인트, 인증 헤더, 복사 가능한 `curl` 예시, 지원 프로토콜 버전 |
| 클라이언트 설정 | `mcpServers` 설정 예시 (복사 버튼 포함) |
| 도구와 권한 | 도구 = 키 Scope ∩ 사용자 권한 ∩ 관리자 허용목록 |
| 문제 해결 | 빈 도구 목록, `mcp_access_denied`, `invalid_origin`, `sse_not_supported`, `isError` 해석 |

`GET /mcp`가 405를 반환하는 것이 정상이라는 점도 적었습니다. 스트림을 제공하지 않는 서버의 규정된 동작인데, 오류로 오해하기 쉽습니다.

## 발견 및 수정한 오류

- 프로토콜 버전을 협상하지 않아 인증 후 모든 호출이 400으로 실패하던 문제
- `2024-11-05` 리비전 클라이언트를 거부하던 문제
- `application/json`만 보내는 클라이언트를 406으로 막던 문제
- JSON-RPC 배치 요청을 잘못된 JSON으로 취급하던 문제
- 도구 실행 실패를 전송 오류로 반환해 모델이 대처할 수 없던 문제
- `no rows in result set` 드라이버 문자열이 REST·MCP 응답에 그대로 노출되던 문제
- `isError` 결과가 요청 로그에 성공으로 기록되던 문제
- 클라이언트가 종료 시 보내는 `DELETE /mcp`와 `notifications/*`에 오류로 응답하던 문제
- 권한 그룹 이름이 한 글자씩 줄바꿈되던 문제
