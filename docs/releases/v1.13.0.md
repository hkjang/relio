## Relio v1.13.0 — 부서 VOC 업무 영역: 회원사 민원과 지식 게이트

한 부서가 공용 고객의 목소리(VOC) 위에서 자기만의 접수 체계를 운영할 수 있게 했습니다. 부서 전용 유형, 접수·해결 항목, 고객 코드를 둡니다. 다른 부서 화면과 영업 지표에서는 분리됩니다. 에이전트는 검토자가 확인한 사례만 진단 근거로 씁니다.

전략사업2부의 회원사 민원 요구사항(필수 10 · 권장 2)을 모두 반영했습니다. 부서 전용 값을 제품 기본값으로 넣지 않고, 관리자가 적용하는 **구성 템플릿** 으로 제공합니다. 적용한 뒤에는 유형·항목·Role을 배포 없이 화면에서 고칠 수 있습니다.

## 요구사항별 반영

| ID | 요구 | 반영 |
|---|---|---|
| R-01 | 접수 항목 3종 | 서비스 구분(필수) · 개발방식('미확인' 포함) · 오류코드. 서버가 필수·허용값을 검증합니다 |
| R-02 | 해결 입력 구조화 | 브라우저 입력창 대신 **해결 처리** 창: 해결 내용 · 근본 원인 · **원인 근거**(확인·추정·미특정, 기본 미선택·필수) · **해결 주체**. "원인이 특정되지 않은 해결도 정상적인 종결입니다" 안내 표시 |
| R-03 | 지식 반영 상태 | 미검토(기본) · 검토중 · 반영 · 제외. 담당자는 조회만 합니다. 해결·종결 건만 '반영' 가능하고, **재처리하면 미검토로 복귀** 합니다 |
| R-04 | 권한 분리 | 새 권한 `voice:knowledge-review`. 검토자 Role에만 부여하며, 개인 키 Scope로 위임할 수 없습니다. 개인 키·OAuth 토큰으로 호출해도 거부되어 **검토자가 화면에서만** 판정합니다 |
| R-05 | 유형 8종 · SLA 미적용 | 유형별 **SLA 적용 스위치**. 끄면 기한을 계산·저장·표시하지 않습니다. 목록은 **경과일** 열과 '14일 이상 경과' 카드, 경과일 필터를 씁니다. 유형은 관리자 화면에서 직접 관리합니다 |
| R-06 | 유사 사례 검색 | MCP `search_voice_knowledge`. 기본은 '반영' 건만 반환하고, `includeUnreviewed` 로 넓힐 수 있으며 상태·원인 근거는 항상 포함합니다. '제외' 건은 반환하지 않습니다 |
| R-07 | 회원사별 이력 | MCP `get_customer_voice_history`. 회원사코드 또는 고객 ID로 종결 건 전체를 최신순으로 반환하며, 게이트를 적용하지 않고 상태 필드는 포함합니다 |
| R-08 | 부서 데이터 분리 | **부서 전용(격리) 업무 영역**: 소유 부서 밖에서는 요청과 영역으로 등록한 회원사가 보이지 않습니다(COMPANY 범위 포함, 시스템 관리자 제외). 이탈 위험도·인텔리전스 Signal/추천·오늘 할 일에서도 제외됩니다 |
| R-10 | MCP 쓰기 | `file_customer_voice`(접수), `record_voice_response`(고객 응대·내부 메모·상위 보고), `resolve_customer_voice`(해결). 쓰기 도구로 표시되고 "담당자 승인 후 실행"을 명시합니다. 지식 반영 상태를 바꾸는 도구는 없습니다 |
| R-11 | 지식 검토 대기 카드 | 목록 상단 카드(종결 · 미검토 건수)와 필터 |
| R-13 | 간이 등록 | 접수 창에서 고객사명·회원사코드로 **검색**하고, 없으면 두 값만으로 그 자리에서 등록·선택합니다. 12자리 형식과 **중복 검사** 를 거치며, 중복이면 기존 회원사명을 알려 줍니다 |
| R-14 | 일괄 등록 | 화면 CSV(열 순서·헤더·탭 허용, 행별 결과) + MCP `import_workspace_customers`. 이미 있는 코드는 건너뛰므로 주기 갱신에 그대로 씁니다 |
| R-09 · R-12 | 제외 | 이메일 접수 경로가 있고 만족도가 선택 입력임을 확인했습니다 |

## 요청 내용과 다르게 구현한 점

- **회원사코드는 고객 마스터의 정식 필드(`고객 코드`)** 로 넣었습니다. 사용자 정의 항목(JSONB)으로는 회사 전체 고유성과 빠른 조회를 보장할 수 없기 때문입니다. 업무 영역이 이름(`회원사코드`)과 형식(`^[0-9]{12}$`)을 정합니다.
- **'고객이 말한 내용' 칸은 기존 필드를 그대로** 씁니다. 에이전트 결과에는 `customerSaid` 로 나갑니다.
- **회원사도 분리했습니다.** 요청은 VOC 기록만 분리하는 것이었습니다. 그런데 회원사 수천 곳을 고객으로 등록하면 인텔리전스 엔진이 회원사마다 "30일 접촉 없음", "의사결정자 없음" 같은 영업 Signal과 추천을 만드는 것을 실측으로 확인했습니다. 그래서 격리 영역으로 등록한 회원사는 다른 부서에 보이지 않고, 영업 계정으로 계산하지도 않습니다.

## 발견해 함께 고친 문제

- **고객 선택이 처음 200곳만 보여 주던 문제**: 기존 접수 창의 고객 목록은 상위 200곳만 불러와, 회원사 목록 대부분을 선택할 수 없었습니다. 입력하며 찾는 검색으로 바꿨습니다.
- **고객 편집 시 조직이 바뀌던 문제**: 고객을 편집하면 담당자의 조직으로 소속이 매번 다시 계산됐습니다. 이제 담당자가 바뀔 때만 조직이 따라갑니다. 부서가 등록한 회원사가 다른 사람의 편집으로 부서 밖으로 옮겨지는 일을 막습니다.

## 관리자 설정

**고객 요청 유형 · 업무 영역** 화면의 **템플릿: 회원사 민원 (본인확인 서비스)** 버튼으로 부서를 고르면 다음을 한 번에 만듭니다.

- 업무 영역: 부서 전용 · 지식 게이트 · 회원사코드 12자리
- 유형 8종(SLA 미적용), 접수 항목 3종 + 해결 주체
- Role 2개: `회원사 민원 담당`, `회원사 민원 검토자`(DEPARTMENT 범위)

만든 Role은 사용자에게 부여하세요. 이미 있는 항목은 건너뛰므로 다시 적용해도 편집한 내용이 바뀌지 않습니다.

## 업그레이드

`016_voice_workspaces.sql` 이 업무 영역 테이블과 다음 열을 추가합니다.

- 요청: 업무 영역, 원인 근거, 지식 반영 상태
- 유형: SLA 스위치
- 사용자 정의 항목: 입력 시점·도움말
- 고객: 고객 코드(고유), 소속 업무 영역

기존 요청은 어느 영역에도 속하지 않고 이전과 똑같이 동작하며, 기존 유형은 모두 SLA 적용 상태로 유지됩니다.

MCP `get_voice_categories` 의 결과가 유형 배열에서 `{categories, workspaces, causeEvidence}` 객체로 바뀌었습니다. 이 도구의 결과를 직접 해석하는 자체 스크립트가 있다면 반영하세요.
